# 마을 / 던전 구조

이 게임의 두 번째 핵심 축.

## 기본 루프
마을(정비 및 준비) → 던전 탐사 → 마을 복귀, 의 정석적인 구조.

- 마을: 장비 정비, NPC와의 관계 상호작용(대화, 퀘스트, 거래), 파티 준비.
- 던전: 칸 기반 전술 전투([[03_combat_system]]) + 관계 시스템이 개입하는 탐사([[01_relationship_system]]).

## 던전 내 이동 방식 (결정됨 — 2026-08-09)
던전 탐사는 그리드에 얽매이지 않는 **자유 이동(8방향)**. 전투가 아닌 상태에서는 필드를 자유롭게 돌아다닌다.
- 적과 시야가 접촉하면(필드 조우식) 전투로 전환되며, 이때 별도 로딩 없이 현재 필드 영역이 그대로 그리드 전투 공간으로 재구성된다(심리스 전환). 전투 자체의 그리드 규칙은 [[03_combat_system]] 참고.

## 던전 생성 방식 (결정됨 — 2026-08-09)
**하이브리드**: 구조/몬스터/함정은 절차적(로그라이크식) 생성, 관계 기반 NPC 조우는 별도 레이어로 분리.

- 이유: 관계 시스템 자체가 콘텐츠 부담이 큰 축이므로, 던전 레벨 디자인까지 전부 손으로 만들면(고정형) 콘텐츠 제작 부담이 이중으로 커짐. 몬스터/함정 배치는 절차적으로 돌려도 재미가 크게 떨어지지 않는 영역이라 자동화하고, 관계 이벤트만 정밀 제어되는 별도 시스템으로 다룬다.
- 완전 고정형(유저 매핑 포함)과 완전 랜덤 두 극단은 기각. 다만 특정 스토리 던전(보스/메인 시나리오)은 예외적으로 고정형으로 만들 가능성은 열어둠 — 추후 필요 시 결정.

## 던전 내 NPC 분류 (결정됨 — 2026-08-09)
던전에 등장하는 NPC는 두 종류로 나눈다.

1. **랜덤 NPC (비네임드)**
   - 절차적으로 등장. 네임드가 아니며, 성향(적대/무시/친밀 등)에 따라 기본 행동이 정해짐.
   - 플레이어와 유의미한 상호작용(공격/강도/도움 등)이 발생하면 [[01_relationship_system]] 의 "승격" 메커니즘을 통해 2번(테이블/트리거형)으로 전환될 수 있음.

2. **테이블/트리거형 NPC (네임드 · 소속 집단 NPC 포함)**
   - 특정 장소·상황·조건에서 랜덤하게(또는 스토리 조건에 따라) 등장.
   - 승격된 구 랜덤 NPC도 이 풀에 편입되어, 이후 동일한 테이블/트리거 로직으로 재조우됨 — 별도 재조우 시스템을 새로 만들 필요 없음.

## NPC 조우 방식 (확정 — 2026-08-13)
던전과 마을은 NPC를 마주치는 방식 자체가 다르다.

### 던전
위 "던전 내 NPC 분류"와 동일 — 실제로 필드를 돌아다니는 개체로 존재하며, 비적대적이면 대화 가능.

### 마을
마을 NPC는 **맵에 직접 배치되지 않는다.** 대신 특정 시설(술집/상점/창고 등)에 입장했을 때, 그 시설에 "있는" NPC와 대화하는 형식 — 던전이 "배치된 개체를 맵에서 찾는" 구조라면, 마을은 "이 시설에 지금 누가 있는가"를 결정하는 로스터(명단) 구조에 가깝다.

- **파티원**: 100% 인카운터. 파티원 전용 장소(아지트/숙소 등)를 두는 방향 — 세부 미정.
- **비파티원 NPC의 시설 출현 여부**는 아래 우선순위로 결정(확정):
  1. **퀘스트 상태** — 진행 중인 퀘스트가 그 NPC의 위치를 특정하게 요구하면 그걸 최우선으로 따름(확정적 배치, 랜덤 아님).
  2. **조건 충족** — NPC별로 정의된 특수 조건(예: 시간대, 관계도, 스토리 플래그 등 — 조건의 구체적 종류는 NPC마다 다를 수 있고 세부는 미정)을 만족하면 그에 따른 위치/등장 결정.
  3. **랜덤** — 위 둘 다 해당 없는 기본 상태에서는 순수 확률 기반으로 그 시설에 출현할지 결정(그 시설의 "단골" 개념). 정확한 확률값은 밸런싱 영역이라 미정.

## 마을 시설 로스터 구현 (v1, 확정 — 2026-08-18)
우선순위 3단계(퀘스트>조건>랜덤) 구조는 코드로 만들어뒀지만, 퀘스트/조건 시스템 자체가 아직 없어서 **v1은 랜덤 티어만 실제로 동작**한다. `FacilityRoster.resolve_present_npcs()`가 후보 NPC 목록을 받아 퀘스트 훅 → 조건 훅(둘 다 항상 `false`를 반환하는 스텁) → 실패 시 `NPCData.appearance_chance` 기반 랜덤 순으로 판정. 시설은 `TownFacility`(마을 씬에 배치되는 마커, `facility_id`+후보 NPC 배열을 가짐) + `town_facility` 그룹으로 여러 시설 확장 가능. 첫 대면 시 `RelationshipManager.register_npc()` 호출로 관계 데이터 생성 확인. 테스트용으로 선술집(`tavern`) 시설 1개 + NPC 2명(`data/npcs/tavern_keeper.tres`, `tavern_patron_dorn.tres`)을 배치.

**다중 NPC 노출 방식** (확정 — 2026-08-18): 최종 비전은 시설 내부에 NPC가 자리(카운터/테이블 등)에 자연스럽게 배치되어 클릭해서 대화하는 방식이지만, 지금은 캐릭터 스탠딩/배경 아트가 없어서 그 방식대로 만들어도 결국 또 플레이스홀더 도형만 배치하는 셈 — 실익 대비 작업량이 안 맞아서 **일단 목록형 UI로 대체**하기로 함(아트 리소스 불필요, 로직도 재사용 가능). 시설에 있는 NPC가 1명이면 목록 없이 바로 그 NPC의 인사말로 진입, 2명 이상이면 이름 목록(버튼)을 보여주고 클릭한 NPC의 인사말로 진입 + 뒤로가기 버튼으로 목록 복귀. 이 로직(로스터 판정 → 선택 → 대화 진입)은 UI 표현과 분리되어 있어서, 나중에 캐릭터 아트가 생겨 인테리어 클릭 방식으로 바꿀 때도 `FacilityRoster`/`Town.gd` 쪽은 그대로 두고 `DialogueBox` UI만 교체하면 됨. 대화 자체는 여전히 **최소 스텁**(NPC 이름 + 고정 인사말 한 줄, 선택지 없음) — 실제 선택지/퀘스트 수주/거래로 이어지는 대화 시스템은 별도 작업. — [[01_relationship_system]]

## 열린 질문 (미정)
- 파티원 전용 장소의 형태(아지트 하나 vs 시설별 파티원 대기 공간 등).
- 비파티원 NPC의 "조건 충족" 종류 목록(시간대/관계도/스토리 플래그 등 구체적으로 뭘 쓸지)과 NPC별 조건 데이터 구조 — v1에서는 항상 `false`인 스텁으로 남겨둠.
- 랜덤 출현 확률의 구체적 수치(밸런싱) — 지금 값(0.9/0.4)은 테스트용 임시값.
- 퀘스트 상태가 NPC 위치를 어떻게 특정하는지 — 퀘스트 시스템 자체가 아직 설계 전이라 추후 그 시스템과 함께 결정.
- 실제 대화 시스템(선택지, 퀘스트 수주/거래 연동) — 지금은 이름+고정 인사말 스텁뿐.
- 시설 내부에 NPC를 실제로 배치해 클릭하는 연출 — 캐릭터 스탠딩 아트가 생기면 목록형 UI를 대체할 후보로 남겨둠(로직은 재사용 가능하도록 이미 분리해둠).
